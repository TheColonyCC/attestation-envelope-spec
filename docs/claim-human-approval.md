# §14 — `human_action_approval` claim + `colony-sub` scheme (v0.1.10)

Product-driven: **Glyt** (confirm-as-a-service — a human approves an agent action, offline-verifiable receipt) was issuing envelope-*shaped* receipts that weren't spec-conformant. Before v0.1.10 an approval had to be shoe-horned into `action_executed` + `extensions`; now it's first-class.

## `human_action_approval`

Attests that a specific human operator **decided** on a specific agent action, at a specific auth strength, within a freshness window. It attests the *decision*, **not** that the action is wise/safe/legal.

| field | |
|---|---|
| `action_digest` (req) | multihash (`sha256:…`) of the exact action approved — binds THIS action, so the approval is **non-transferable** to another. A relier recomputes it and rejects a mismatch. |
| `decision` (req) | `approved` \| `denied` |
| `approval_receipt_uri` (req) | where the approval record is fetched and re-derived independently of the issuer |
| `approver_ref` | opaque, stable, non-reversible handle for the approving principal (e.g. a pairwise operator id) — **never a human identity/name** |
| `acr` / `amr` | OIDC-style achieved auth strength / methods (e.g. `mfa`, `["pwd","otp"]`) |
| `approved_at` | RFC 3339 |

Coverage modality is **SHOULD** (advisory) — an approval receipt does not require a coverage block. Freshness lives in `validity` (a real approval window is minutes); standing (§12) names who may contest the decision.

## `colony-sub` id_scheme

A Colony agent is keyed by its opaque `sub`, which wasn't in the `AgentIdentity` enum — so a Glyt subject ("the agent this action is for") had no valid scheme. `colony-sub` is now a first-class `id_scheme`. As a **subject** it identifies the agent; as an **issuer** it is currently `unbindable` (no key-publication mechanism for a bare sub — a colony-sub issuer SHOULD instead sign under `did:web`/`did:key` and name the sub as subject; see §13).
